# Database Foundation

## Goal

Establish a safe, reproducible PostgreSQL persistence layer for the .NET version of DevStash using Entity Framework Core and the existing Neon development database infrastructure.

This feature creates the database foundation only. Authentication endpoints, item CRUD, search, and React integration belong to later features.

## Learning Outcomes

By completing this feature, we should understand:

- How an entity differs from an API request or response DTO.
- How `DbContext` and `DbSet<T>` represent a unit of work and queryable tables.
- How EF Core translates LINQ expressions into PostgreSQL SQL.
- How dependency injection creates and scopes a `DbContext` per HTTP request.
- How code-first migrations describe and apply schema changes.
- How local secrets and environment-based configuration keep connection strings out of Git.
- Why the .NET rebuild uses an isolated PostgreSQL schema instead of sharing Prisma-managed tables.

## Technology

- Entity Framework Core 10
- Npgsql Entity Framework Core provider for PostgreSQL
- ASP.NET Core Identity Entity Framework Core persistence
- Neon PostgreSQL development branch
- A repository-local `dotnet-ef` tool manifest

Package versions must be compatible with the repository's pinned .NET 10 SDK. Do not use prerelease packages unless explicitly approved.

## Configuration Requirements

- Read the connection string from `ConnectionStrings:DevStashDatabase`.
- Store the local connection string with .NET user secrets or an environment variable; never commit it.
- Add a non-secret placeholder to the committed configuration where useful.
- Register the database context through ASP.NET Core dependency injection with a scoped lifetime.
- Configure Npgsql retries suitable for transient serverless database failures, without hiding permanent configuration errors.
- Do not apply migrations automatically during normal application startup.

## Initial Data Model

Use `Guid` primary keys generated by the .NET application. Use UTC timestamps for persisted dates.

### ApplicationUser

Create an ASP.NET Core Identity-compatible user entity so later authentication work does not require replacing the ownership model.

This feature creates persistence only; it does not expose registration, login, logout, cookie, email-verification, or password-reset endpoints.

### ItemType

- `Id`
- `Name`
- `Slug`
- Optional icon and color
- `IsSystem`
- Optional `UserId` for future custom user-owned types
- Created and updated timestamps

System item types have no owner. Seed these built-in types:

- Snippet
- Prompt
- Note
- Command
- File
- Image
- Link

### Item

- `Id`
- `Title`
- Optional description
- Content type
- Optional content, language, and URL
- Favorite and pinned flags
- Optional last-used timestamp
- Required owner (`ApplicationUser`)
- Required `ItemType`
- Created and updated timestamps

File-storage metadata, uploads, AI fields, and billing fields are outside this feature.

### Collection

- `Id`
- `Name`
- `Slug`
- Optional description
- Favorite flag
- Required owner
- Created and updated timestamps

### Tag

- `Id`
- `Name`
- `Slug`
- Required owner
- Created and updated timestamps

### ItemCollection

Explicit many-to-many join entity between Items and Collections.

- Composite key: `ItemId`, `CollectionId`
- Created timestamp

### ItemTag

Explicit many-to-many join entity between Items and Tags.

- Composite key: `ItemId`, `TagId`

## Relationship and Integrity Rules

- Deleting a user cascades to their items, collections, tags, and custom item types.
- Deleting an item cascades to its collection and tag join rows.
- Deleting a collection or tag removes join rows but does not delete items.
- Deleting an item type that is referenced by an item is restricted.
- Collection slugs are unique per user.
- Tag slugs are unique per user.
- Custom item-type slugs are unique per user.
- System item-type slugs are globally unique.
- Add indexes for common ownership and sorting queries, including user plus updated timestamp.
- Use explicit EF Core configurations so table names, column names, keys, indexes, and delete behavior are reviewable.

## Migration Requirements

- Create a repository-local tool manifest for `dotnet-ef`.
- Generate an initial migration with a descriptive name such as `InitialDatabaseFoundation`.
- Confirm that the generated migration creates or targets only `devstash_dotnet`.
- Confirm that the EF migrations-history table is stored in `devstash_dotnet`.
- Review generated migration code and SQL before applying it.
- Apply the migration only to Neon branch `br-aged-queen-abnc2h82`.
- Do not manually edit the existing Prisma migration history.

## Testing and Verification

- `dotnet restore` succeeds.
- `dotnet build --no-restore` succeeds without warnings or errors.
- Existing API integration tests continue to pass.
- Add focused tests that verify important EF Core model metadata such as keys, unique indexes, relationships, and delete behavior without depending on production.
- The initial migration can be generated successfully.
- Generated SQL targets the `devstash_dotnet` schema and contains no destructive operations against `public`.
- After explicit development migration, verify that the expected tables and seven system item types exist in `devstash_dotnet`.
- Keep `/health` as an application liveness check. A database-readiness endpoint may be designed separately rather than making all tests depend on live Neon access.

## Acceptance Criteria

- The API uses an EF Core `DbContext` registered through dependency injection.
- Npgsql reads its connection string from secure configuration.
- Identity-compatible user persistence and the initial DevStash domain entities are modeled.
- Entity configurations enforce the required keys, ownership, uniqueness, indexes, and delete behavior.
- All EF-managed objects, including migration history, are isolated in `devstash_dotnet`.
- The initial migration and its SQL have been reviewed before being applied to development.
- Seven built-in item types are seeded reproducibly.
- Backend build and tests pass.
- No production resources or existing Prisma-managed tables are changed.
